# Tenant contract

Typed definition: `curator/contracts/tenant.py`
Fixtures: `tests/fixtures/contracts/tenant/`
Freezes: plan sections "Privacy and security boundary" and the Locked WHAT
privacy row. Criteria: SC-13, SC-27, SC-32.

## Purpose

Every private record in the system carries provider-neutral `tenant_id`,
`user_id`, and `actor_id`. That is the whole point of this contract: identity is
decided here, once, so that a later sign-in provider, a second user, or a public
product is an adapter and a new tenant row rather than a schema change.

Today there is exactly one tenant, private, with one human user. The contract is
written for many because retrofitting tenancy after the ledger exists is the
expensive version.

## Records

### `Ownership`

The shared shape EVERY private record inherits. Four fields, all required, all
flat (one column each in SQL, one key each in a fixture). A private record does
not re-declare them and cannot carry three of the four.

| Field | Type | Constraint |
|---|---|---|
| `tenant_id` | str | Required, non-empty. The isolation boundary the row belongs to. |
| `actor_id` | str | Required, non-empty. WHO WROTE the row. |
| `actor_kind` | `ActorKind` | Required. `human`, `agent`, or `system`. |
| `user_id` | str or null | Required as a KEY. The human the row is ABOUT. Never blank: a non-blank id, or null where the two-tier rule below permits null. |

Read the last two together. `actor_id` is the writer; `user_id` is the human.
They answer different questions, and a system writer does not erase the human
subject: a profile snapshot computed by the normalizer is still about one
person.

Every id must be CANONICAL, which is three rules, not one. `not null`,
`non-blank` and `canonical` each close a different hole:

| Rule | Rejects | Why |
|---|---|---|
| not null | missing key | absence must fail, never default |
| non-blank | `""`, `"   "` | two extra encodings of "no human" in a rule that has one, so a sweep filtering `user_id is null` misses the blank rows |
| canonical | `" user-1 "`, `"\tuser-1"`, `"user\u200b1"`, `"\u3000"` | two encodings of one SUBJECT, so a per-person delete keyed on the canonical spelling misses the padded or zero-width row |

Canonical means: equal to its own stripped value, at least one non-whitespace
character, no code point in `INVISIBLE_ID_CODE_POINT_RANGES`
(`curator/contracts/__init__.py`), no unpaired surrogate, and Unicode
normalization form NFC.

The invisible list is every Unicode `Zs`, `Zl`, `Zp`, `Cc` and `Cf` character,
so U+0020, U+00A0, U+2028, U+2029, U+3000, U+200B through U+200D, U+2060 and
U+FEFF are all refused. `Zl` and `Zp` joined on 2026-09-02: the list was
`Zs`/`Cc`/`Cf` only, and Python's `str.strip()` removes U+2028 while `btrim`
does not, so `"user-1\u2028"` was rejected by Python and accepted by the
database. ASCII space is in `Zs`, so an INTERNAL space is refused too: an
identifier is a key, not a label. NFC is that same argument in the encoding
dimension: `"jos\u00e9-1"` and `"jose\u0301-1"` render identically, so they are
one subject in two rows and a per-person delete keyed on the composed spelling
misses the decomposed one. Consequences worth naming, all of them fallout from
"a key, not a label": emoji ZWJ sequences, emoji flag TAG sequences and display
names carrying a bidi mark are all refused; plain CJK, kana, hangul, Arabic,
combining marks, dashes, underscores, uuids and single emoji are accepted.

The Python predicate and the SQL `check` constraints are two renderings of that
one frozen list, generated by `curator.ownership.ownership_id_sql_check`, and a
freeze test regenerates the migration's text and fails on drift. The old SQL
form was `btrim(x) <> ''`, which strips SPACES ONLY: tab, newline, U+00A0 and
U+3000 were all accepted by the database while both Python validators rejected
them. ONE deliberate asymmetry remains: unpaired surrogates are refused by the
Python predicate and not by the SQL class, because a UTF8 database cannot store
one at all (the write fails on encoding, before any check runs).

#### The two-tier rule: when may `user_id` be null?

One question decides it: **must a "delete everything about me" request find and
delete this row?**

<!-- generated: ownership-classification -->
| Tier | `user_id` | Records |
|---|---|---|
| SUBJECT-BOUND (yes) | REQUIRED non-blank, whatever wrote the row | `ArtifactRelation`, `ArtifactVersion`, `AuthorizationAudit`, `CorrectionEvent`, `EvidenceItem`, `KnowledgeArtifact`, `LearningEvent`, `MirrorReceipt`, `OutputReceipt`, `ProfileSnapshot`, `PublicationAuthorization`, `PublicationRecord`, `PublishingBasket`, `RawImport`, `Slate`, and a `ReceiptEnvelope` whose `kind` is one of `deletion`, `import_inventory`, `ranking` |
| SUBJECTLESS (no) | May be null, and then ONLY when `actor_kind` is `system` | `LaneCandidate`, `MergedCandidate`, `NormalizedSourceDocument`, `SourceCheckpoint`, `SourcePluginRegistration`, `StoryRecord`, and a `ReceiptEnvelope` whose `kind` is one of `host_limits` |
<!-- end generated -->

On a subjectless record a human or agent actor still requires a non-blank
`user_id`: the tier relaxes the rule for the system only.

Why the tiers exist. `tenant_members` is keyed `(tenant_id, auth_uid)`, so a
tenant can hold more than one human. If evidence, snapshots, and mirror receipts
named only their WRITER, they would be unattributable to a person the day a
second member exists, and `deletion_receipts` could not prove a per-person
deletion complete. The per-RUN intermediates (`LaneCandidate`, `StoryRecord`,
`MergedCandidate`) stay subjectless because they exist before any
personalization and are reachable by join from the slate they feed, so a null
there costs a join rather than correctness. `Slate` and a `ranking` envelope
are NOT in that group (moved 2026-09-02): a slate is one person's ranked
edition, and its only link to a human, `profile_snapshot_id`, is nullable, so
a cold-start slate would name nobody and nothing would name it.

The classification is frozen as data in `curator/contracts/__init__.py`
(`SUBJECT_BOUND_RECORDS`, `SUBJECTLESS_RECORDS`, `KIND_BOUND_RECORDS`,
`SUBJECT_BOUND_RECEIPT_KINDS`, `SUBJECTLESS_RECEIPT_KINDS`, and a written reason
per class in `OWNERSHIP_CLASSIFICATION_REASONS`).
`test_every_owned_record_is_classified_exactly_once` fails if an owned record is
in no tier or in two, so a new private record cannot land unclassified and fall
into the permissive tier by default.

#### Where the rule is enforced

| Layer | Implementation |
|---|---|
| Frozen fixture corpus | `_invariant_ownership` in `tests/test_contract_freeze.py` |
| Runtime write paths | `ownership_violations` in `curator/ownership.py` (re-exported from `curator/ledger/ownership.py`), called by every `InMemoryLedgerStore.append_*`, `record_deletion_receipt`, and the checkpoint store on BOTH `load` and `advance` |
| Storage | per-column canonical `check` constraints (generated by `curator.ownership.ownership_id_sql_check`) and `user_id text not null` in `supabase/migrations/202609020001_learning_ledger.sql` |

The contracts package stays DECLARATIVE (no `__post_init__`, no behavior), so
the runtime guard lives outside it and RECOMPUTES the rule rather than trusting
the caller. `test_the_two_ownership_validators_agree_on_every_fixture` runs both
implementations over the whole fixture corpus and compares verdicts, so the two
cannot drift apart.

None of the four carries a default. That is the point: an optional guard field
skips its own check when it is simply omitted, which is the bypass class the
contract-freeze re-review found. Absence fails structural validation instead.

Which records inherit it: `curator.contracts.OWNED_RECORDS`. Membership is
derived from the class hierarchy, and
`tests/test_contract_freeze.py::test_every_private_record_inherits_the_shared_ownership_shape`
fails if a contract dataclass carries tenant, actor, or user semantics without
either inheriting `Ownership` or appearing in that test's exempt map with a
written reason. Membership is decided by NAME PATTERN, nested dataclass fields
included, not by two exact names: matching two exact names let
`PublicationAuthorization` (tenant nested inside `identity`, actor spelled
`approved_by_actor_id`) and `PublicationRecord` through in silence.

The matcher was widened on 2026-09-02, because `*tenant_id` / `*actor_id` /
`*user_id` alone still missed a field named `actor_identity`: a record could
rename its actor binding and become invisible to both the ownership shape and
the exemption review. It now matches, case-insensitively, any field name ending
in `tenant_id`, `actor_id`, `user_id`, `_actor`, `_tenant`, `_user`,
`_principal`, `_owner`, or `_subject`, plus the whole names `actor_identity`,
`actor_ref`, `tenant_ref`, `user_ref`, `principal_id`, `owner_id`, and
`subject_id`. Every existing exemption was re-reviewed against the wider
matcher and each kept its written reason; the one new hit is
`Tenant.is_public_projection_tenant`, a boolean flag whose name ends in
`_tenant`, and `Tenant` was already exempt as the isolation boundary itself. The exempt records are the identity records themselves
(`Tenant`, `User`, `Actor`, `TenantMembership`), an at-most-once key
(`PublicationIdentity`), a request, its response row and the response envelope
(`SearchQuery`, `SearchResult`, `SearchResponse`), and the caller's
asserted-and-then-verified identity (`PrincipalClaims`).

### `Tenant`

| Field | Type | Constraint |
|---|---|---|
| `tenant_id` | str | Required. Stable, opaque, never a provider subject. |
| `display_name` | str | Required. Human label only; carries no authority. |
| `default_publication_class` | `PublicationClass` | Required. `private` or `public`. No third value exists. |
| `created_at` | datetime | Required, timezone-aware UTC. |
| `is_public_projection_tenant` | bool | Default `false`. |

### `User`

| Field | Type | Constraint |
|---|---|---|
| `user_id` | str | Required. Stable across any future identity provider. |
| `tenant_id` | str | Required. A user belongs to exactly one tenant. |
| `created_at` | datetime | Required. |
| `display_name` | str | Optional, default empty. |

### `Actor`

| Field | Type | Constraint |
|---|---|---|
| `actor_id` | str | Required. Referenced by every event, artifact, receipt, and audit row. |
| `tenant_id` | str | Required. |
| `actor_kind` | `ActorKind` | Required. `human`, `agent`, or `system`. |
| `created_at` | datetime | Required. |
| `user_id` | str or null | Required as a KEY, no default. The human this actor acts for. Non-blank for a `human` or `agent` actor; null only for `system`. |
| `label` | str | Optional. |

`Actor` is exempt from `Ownership` (it is the record an `actor_id` points AT)
but obeys the same null rule, enforced by the `Actor` invariant. It is the
binding that makes an agent-written record attributable, so an agent `Actor`
with no `user_id` would silently unbind every row that actor writes. The field
carries NO default for the same reason every ownership field carries none: an
optional guard skips its own check when omitted.

### `TenantMembership`

| Field | Type | Constraint |
|---|---|---|
| `membership_id` | str | Required. |
| `tenant_id`, `principal_id`, `actor_id` | str | Required. |
| `roles` | tuple of str | Default empty. Roles gate actions; scopes gate credentials. |
| `active` | bool | Default `true`. |
| `revoked_at` | datetime or null | Set on revocation. The row is never deleted. |

## Invariants

1. Every private record references a `tenant_id`. A record without one cannot be
   isolated and therefore cannot exist. Stated as a shape rather than a rule
   since 2026-09-02: it inherits `Ownership`, so all four ownership fields are
   present or the record does not validate.
2. `is_public_projection_tenant` is not a switch on the private tenant. A public
   product is a SEPARATE tenant row with its own membership and its own
   projections; it cannot query raw imports, private events, private profiles,
   questions, or unpublished artifacts.
3. An agent actor is always distinguishable from the human it acts for. They are
   separate `actor_id` values sharing a `user_id`.
4. Revocation is a state change plus a timestamp, never a delete, so an audit
   trail written under a since-revoked membership stays interpretable.
5. A provider subject (an OAuth `sub`, for instance) is held by the identity
   adapter and mapped onto `user_id`. It never becomes a core field, which is
   what makes SC-32 a mapping exercise rather than a migration.

## Freeze notes

- **2026-09-02, `Ownership` added.** The plan's privacy boundary says every
  private record carries provider-neutral `tenant_id`, `user_id`, and
  `actor_id`. Before this, no record carried `user_id` at all,
  `ReceiptEnvelope.actor_id` defaulted to the empty string, `EvidenceItem` had
  no actor, `RawImport` spelled it `owner_actor_id`, and `ArtifactVersion` had
  no `tenant_id`. One inherited shape replaces five near-misses, and a freeze
  test is what keeps a sixth from appearing.
- **2026-09-02, name collision resolved.** `tenant_members.user_id` in
  `supabase/migrations/202609020001_learning_ledger.sql` held an `auth.users`
  uuid, which is an identity PROVIDER SUBJECT, while this contract's `user_id`
  is a stable provider-neutral text id. Two different things cannot share one
  column name in one schema, so the auth subject is now `auth_uid` and
  `user_id` means this contract's value everywhere. Mapping one onto the other
  is the identity adapter's job (SC-32) and is DEFERRED: nothing joins them
  yet, and row isolation is still keyed on tenant membership alone.
- The plan names `tenant_id`, `user_id`, and `actor_id` but does not enumerate
  role names. Roles are left as free strings here, deliberately: the
  authorization contract gates on SCOPES, which are enumerated and closed, so an
  unrecognised role grants nothing. Enumerating roles would be a second closed
  vocabulary doing the same job.
- `PublicationClass` has exactly two members. A "shared" or "unlisted" class was
  not created, because the plan's boundary is binary and a third value would
  need its own projection rules.
- Grade: B that the repository has no tenant column today (the shipped
  `user_preferences` table keys on a user id only; see
  `personalization-reconciliation.md`). C that this shape is sufficient at
  multi-user scale, which remains an unverified technical claim. This contract
  does not schedule that work.
