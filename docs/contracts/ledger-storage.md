# Learning ledger storage (phase 4, first slice)

## What the migration implements

`supabase/migrations/202609020001_learning_ledger.sql` creates the storage
for the frozen event, evidence, artifact, and receipt contracts
(`curator/contracts/{event,evidence,artifact,receipt,mirror,tenant}.py`):
`learning_events`, `correction_events`, `evidence_items`, `raw_imports`,
`knowledge_artifacts`, `artifact_versions`, `artifact_relations`,
`deletion_receipts`, `mirror_receipts`, plus a minimal `tenant_members` table
that every row-level security policy is keyed on. Columns match the frozen
dataclass field names, required fields are `NOT NULL`, and every closed enum
(`ActorKind`, `EventType`, `EvidenceClass`, `EvidenceOrigin`, `ConfidenceBand`,
`CorrectionAction`, `RetentionState`, `ArtifactType`, `ArtifactStatus`,
`PublicationClass`, `ReceiptState`, `MirrorState`) is a `CHECK` constraint,
not a free-text column. Every table has RLS enabled and forced, default
grants revoked from `public` and `anon`, and owner-scoped `SELECT`/`INSERT`
policies (plus `UPDATE` where the row's own state legitimately changes)
keyed on `tenant_members`. Nothing in this migration grants `DELETE` to
`authenticated` on any table: the ledger's own rows are never physically
removed, only superseded or marked by a later row.

## The four ownership columns (2026-09-02)

Every table that stores a private record carries the same four columns,
because the frozen dataclasses now inherit one shared `Ownership` shape
(`curator/contracts/tenant.py`, described in `tenant.md`):

| Column | Type | Rule |
|---|---|---|
| `tenant_id` | `text not null` | The isolation boundary. |
| `actor_id` | `text not null` | Who wrote the row. **No default.** |
| `actor_kind` | `text not null` | `check (actor_kind in ('human','agent','system'))`. |
| `user_id` | `text not null` | The human the row is ABOUT. |

All nine tables here are SUBJECT-BOUND (see the two-tier rule in `tenant.md`):
a "delete everything about me" request must be able to find every one of these
rows, so `user_id` is `not null` whatever wrote the row. The
`check (actor_kind = 'system' or user_id is not null)` form these tables used to
carry is GONE: it let a normalizer-written row about one person name nobody,
which makes a per-person deletion impossible to execute or to prove complete.
Subjectless records (source checkpoints, plugin registry rows, normalized public
documents, pipeline intermediates) may carry a null `user_id` and have no table
here yet.

**Blank is not null, and non-blank is not canonical.** `not null`, `non-blank`
and `canonical` are three different rules, so each of `tenant_id`, `actor_id`
and `user_id` carries a four-clause check on every table: equal to its own
`btrim`, at least one non-space character, no invisible code point, and
`is nfc normalized`. The text is GENERATED by
`curator.ownership.ownership_id_sql_check`; do not hand edit it, and see
`tenant.md` for what "canonical" means. Without the first clause, `actor_id = ''`
(the exact unattributed value this shape removed as a column default) and
`user_id = ''` were both legal rows, and a deletion sweep filtering
`user_id is null` silently missed the blank ones. The earlier form was
`check (btrim(<column>) <> '')`, and `btrim` with no second argument strips
SPACES ONLY, so a tab, a newline, U+00A0 or U+3000 was accepted by the database
while both Python validators rejected it. The `is nfc normalized` clause needs
PostgreSQL 13 or later on a UTF8 database and no extension.

Five specific changes came with the shape.

**`raw_imports.owner_actor_id` became `actor_id`.** One field, one spelling.

**`deletion_receipts.actor_id` lost its `default ''`.** An unattributed
receipt used to be that column's own default value, so a writer that never set
it produced a receipt naming nobody.

**`artifact_versions` gained `tenant_id`, `actor_kind`, and `user_id`.** It
previously had no tenant column at all and proved tenancy only by joining to
its parent artifact. Two things now stop the row and its parent from
disagreeing: `knowledge_artifacts` carries `unique (artifact_id, tenant_id)`,
and `artifact_versions` carries a composite `foreign key (artifact_id,
tenant_id)` against it, so a version physically cannot claim a different
tenant than its artifact. Its RLS policies require BOTH the historical parent
join AND `public.is_tenant_member(tenant_id)` directly, which is what makes
the new column load-bearing rather than decorative.

**Every parent link is a COMPOSITE `(parent_id, tenant_id)` foreign key.** The
composite form above was originally written once and its three siblings were
left single-column, so a child could still name a parent in another tenant.
All four now match:

| Child | Column | Parent |
|---|---|---|
| `evidence_items` | `raw_import_id` | `raw_imports` |
| `artifact_versions` | `artifact_id` | `knowledge_artifacts` |
| `artifact_relations` | `artifact_id` | `knowledge_artifacts` |
| `mirror_receipts` | `artifact_id` | `knowledge_artifacts` |

`raw_imports` gained the `unique (raw_import_id, tenant_id)` key these need as a
target. This is not theoretical: Postgres checks referential integrity with row
security OFF, so RLS does not stop a tenant-A member inserting a child whose
parent lives in tenant B, and a single-column FK also leaks an existence oracle
for another tenant's ids (the insert succeeds or fails depending on whether the
id exists).

**MATCH SIMPLE on the nullable link, deliberately.** `evidence_items.raw_import_id`
is nullable, and a composite foreign key with any null column is NOT enforced
under the default `MATCH SIMPLE`. That is the behaviour we want: live evidence
has no import to point at, so the row skips the constraint rather than needing a
placeholder parent. The half-null case (a present `raw_import_id` with a null
`tenant_id`, which MATCH SIMPLE would also skip) cannot arise, because
`tenant_id` is `not null` on that table. No extra check constraint is added for
it; a `check (raw_import_id is null or tenant_id is not null)` would be
trivially true and would read as protection it does not provide.

## Name collision: `tenant_members.user_id` became `auth_uid`

`tenant_members` held an `auth.users` uuid in a column called `user_id`. That
is an identity PROVIDER SUBJECT. The contract's `user_id` is a stable,
provider-neutral text id that now appears on every private record. Two
different things cannot share one column name in one schema, so the auth
subject is `auth_uid` and `user_id` means the contract's value everywhere
else. `public.is_tenant_member()` and the membership `SELECT` policy read the
renamed column.

Mapping an auth subject onto a contract `user_id` is the identity adapter's
job (SC-32) and is **deferred**: no table joins the two, and nothing reads
`user_id` for authorization. Row isolation is still keyed on tenant
membership alone, exactly as before.

The migration was edited IN PLACE rather than superseded by a second
migration, on the understanding that it has not been applied to any
environment. **That is grade C, not grade B**: it rests on stored slice notes,
and no live check of `supabase_migrations.schema_migrations` for version
`202609020001` has been run against the real project. Anyone applying this file
should confirm that first. If it HAS been applied anywhere, the in-place edit is
silently wrong and needs a superseding migration instead.

The SQL itself is grade B (proven by reading, plus the text-level tests that
parse this file as data). It has never been executed against a Postgres
instance, so the DDL, the new check constraints, the composite foreign keys, and
the RLS behaviour are all unproven at runtime.

## Append-only guarantee and how retraction works

`learning_events`, `correction_events`, `evidence_items`, and
`artifact_versions` are the actual history. Each carries a trigger
(`reject_ledger_mutation`) that raises on `UPDATE` or `DELETE`, so even a
service-role connection cannot edit history in place, plus an explicit
`REVOKE UPDATE, DELETE ... FROM authenticated` as a second, independent
barrier. A mistake or a user's "I didn't mean that" is never fixed by editing
the original row. It is fixed by appending a `CorrectionEvent` (or, in the
evidence graph, setting a later row's `retracted_by_event_id` to point back)
that names the row it corrects. `LedgerStore.effective_events(tenant_id,
as_of)` is the read-side of this: it returns every event recorded at or
before the watermark, minus any event whose id is the `target_id` of a
`retract` correction that occurred at or before the same watermark. The
retracted row itself is still readable by id; it is only excluded from this
projection. `DeletionReceipt` settlement is guarded the same way: a receipt
cannot claim `state = settled` while any of its listed projections is
unresolved, enforced both in SQL (`deletion_receipt_may_settle`) and in the
in-memory store, mirroring the invariant in
`tests/test_contract_freeze.py::_invariant_deletion_receipt`.

## Idempotency identity is per-user, not only per-tenant (2026-09-02, round 6)

`learning_events` carries `unique (tenant_id, user_id, idempotency_key)`, not
`unique (tenant_id, idempotency_key)`. The tenant-only form let two different
users in one tenant collide on the same key TEXT: whichever event landed first
silently absorbed the second user's retry (the SQL half would raise a unique
violation, loud; `InMemoryLedgerStore` returned the OTHER user's row, silent,
which is exactly the drift the in-memory store exists to catch, not cause).
`curator/ledger/memory.py` keys its index on the same triple. A client may
reuse the same key text across different users safely; see
`docs/contracts/event.md` for the full derivation rule.

## Deferred, carried forward every round

Restated here as the one list nothing leaves without a recorded resolution
(round 6 found four of these had silently fallen off every receipt since
round 1; see `A7-ownership-fix6-receipt.md`). Each entry: item, one-line
reason it is open, not blocking today.

- **`is_tenant_member` is `security invoker`.** A `definer`-style bypass of
  RLS is not needed while every caller is `authenticated`; revisit if a
  service-role caller is ever added that must check membership without its
  own row visibility.
- **Only 9 of 22 owned contract classes have tables.** The rest land with
  their own stores as later phase-4 slices ship (profile snapshots, search
  indexes, public projections, mirrors' write path).
- **No foreign key binds a row's `(actor_id, user_id)` to an `Actor` row.**
  There is no `actors` table yet; adding one and the FK is the identity
  adapter's job (SC-32), tracked separately from this ledger slice.
- **`*_update_own` policies could re-attribute a row.** Any tenant member may
  `update ... set actor_id / actor_kind / user_id` after insert on the tables
  that allow `UPDATE` at all, rewriting the attribution these columns exist
  to hold. Attribution-column immutability is a later trigger
  (`check (actor_id = old.actor_id ...)` or an `on update` guard), scheduled
  not blocked: today's schema has no live rows to re-attribute.
- **`Actor` remains constructible with `actor_kind: agent, user_id: null`.**
  Grade C: there is no persistence path for `Actor` yet (see the two items
  above), so this has no live blast radius to reproduce against.
- **The migration is applied nowhere.** No live query of
  `supabase_migrations.schema_migrations` for `202609020001` has been run
  across six rounds; see "Name collision" above.
- **`JsonFileCheckpointStore.advance` has a lost-update race and a shared
  temp filename** (`curator/sources/checkpoint.py`). Two concurrent runners
  can silently discard each other's advance, or interleave writes to the same
  `.tmp` path. Out of blast radius today: the store is used by nothing outside
  its own module and tests (`JsonFileCheckpointStore`/`CheckpointStore` have
  no other caller in the repo), so this is a fix-when-wired item, not a live
  hole.
- **The existing `user_preferences` migration is additive and separate.**
  `202608290001_user_preferences.sql` predates this ledger migration and is not
  folded into it. Reconcile its provider-bound user key with the shared
  ownership shape when the identity adapter lands, without rewriting the
  already frozen preference surface in this slice.
- **A per-user normalized document needs an explicit discriminator or trigger.**
  `NormalizedSourceDocument` is subjectless only while it describes public
  source material. If a later store adds reader-specific normalized content,
  it must either use a distinct subject-bound record type or enforce the split
  with a storage trigger so a per-user row cannot hide in the subjectless tier.

## What is NOT yet built

- Profile snapshot builder (reading `evidence_items` and `learning_events`
  into a `ProfileSnapshot`).
- Rebuild / replay pipeline that recomputes a snapshot from the effective
  event set after a correction invalidates one.
- Search index over artifacts or evidence.
- Mirror write path (the `mirror_receipts` table exists; nothing writes to
  an external target yet).
- A Postgres-backed `LedgerStore` implementation; only `InMemoryLedgerStore`
  exists today, for tests and local dry runs.
