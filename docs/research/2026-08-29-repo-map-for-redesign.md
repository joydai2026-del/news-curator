# news-curator repo map (for UI/UX redesign planning)
Repo: /Users/joyd/news-curator, branch main. All facts below verified directly against the repo source and the two decision docs named in the task. Grades: A = proven in production, B = proven in source, C = not verified.

## 1. Frontend rendering (Grade B, source-verified)

- Static site generator: none. `curator/render.py` builds a single `site/index.html` as one Python f-string (no template engine, no framework, no build step, no JS bundler).
- Output location: `site/index.html` (gitignored, `site/` says "produced by CI, not committed to main"). `site/.nojekyll` also written. `site/` currently on disk has an old sample (2 files, 16K).
- Static hand-authored pages: `static/privacy.html` (only file there), copied into `site/` at build time by the `curate.yml` workflow ("Copy static pages" step). This is the privacy page required by the published Gmail OAuth app.
- CSS and JS are inline, embedded as Python string constants `CSS` and `JS` inside `render.py` (lines ~72-353) -- no external .css/.js files at all.
- Page structure (from `render_html`): header (site name, "Built <date> . scheduled hourly . N stories", a staleness indicator computed client-side), a `.tools` bar with category chip nav (`<nav aria-label="Categories">`) plus a search `<input class="q">`, a `.grid` of `<article class="card">` elements, an `.empty` state, and a footer with an accuracy disclaimer, a health-line (per-tier fetch status), an "Add a topic" link (deep-links to GitHub's file editor for `topics.yaml`), and an "Open source on GitHub" link.
- Cards ("Discover cards", v2 design): 3:2 image crop (or a typographic gradient fallback panel using a per-category hue), eyebrow (category label), headline (3-line clamp), 2-line description, meta row (echo badge "N sources", source/via label, relative age), a chevron "Open" button. Clicking a card (outside links) expands it in place to full grid width showing full description, source, exact timestamp, "Also covered by" cluster links, matched keywords, and a "Read at source"/"Close" action row.
- Client-side JS (~110 lines, vanilla, no dependencies): builds a search index from the DOM itself (headline+description text, lowercased) rather than shipping a duplicate JSON index; category filtering happens via `data-topics` attribute + a `hidden` toggle; per-tab ranking uses `data-rank-<slug>` attributes read into `element.style.order` (CSS grid order) so there is exactly one DOM node per story reused across every tab, with no re-sort/reflow; open/close state per card; `localStorage` remembers the last-selected tab (`nc-tab`); a staleness banner recomputes "last build Nh ago" in the reader's browser (never baked in at build time).
- No search index file, no separate JSON API, no backend of any kind -- the entire "search" and "filter" experience is client-side over the already-rendered DOM.

## 2. Data model (Grade B, source-verified)

- No database (no SQLite, no external DB). Everything lives in flat files, some committed to git, most ephemeral per run:
  - `image_cache.json` (committed) -- preview-image lookup cache, keyed by canonical URL.
  - `newsletter_state.json` (committed) -- newsletter lane cursor: watermark timestamp + salted content hashes only (privacy-scoped, see §3/§6).
  - Everything else (fetched articles, ranked lists) is in-memory for the duration of one pipeline run and never persisted as raw data -- only the rendered `site/index.html` and the two files above survive a run.
- Per-item fields (`curator/models.py` `Item` dataclass): `title`, `url`, `canonical_url`, `source_id`, `source_name`, `published_at` (tz-aware UTC), `platform`, `source_weight`, `score` (native popularity, optional), `is_aggregator`, `time_is_estimated`, `image_url` (hotlinked, may be empty), `description` (source's own summary only, never generated), `is_newsletter`, `newsletter_sender`, `echo_platforms` (set, grows only from URL-identical merges), `native_categories`, `matched_keywords`, `cluster` (list of `{source_name, url}` for merged-away duplicate URLs of the same story).
- No `category`/`topic` field on the item itself -- category membership is computed downstream by `assign_categories` (keyword match or native-feed membership) and folded per-story into a `data-topics` set of slugs at render time (one card can belong to several categories).
- No `language` field anywhere on `Item` or in config -- confirmed by grep, no i18n/locale/language handling exists in the codebase (only a hardcoded `Accept-Language: en` header on image-meta fetches, and one keyword phrase "large language model"). See §5.
- Images: hotlinked, never downloaded or rehosted. `image_cache.json` stores only `{image: url|null, outcome: "ok"|"none"|"error", checked_at, seen_at}` per canonical URL -- literally the URL string and timestamps, no binary/image bytes. Two sources of the image URL: (1) feed-declared media (RSS `media:content`/enclosure, free, tried first), (2) the publisher's own `og:image`/`twitter:image` meta tag, fetched by streaming just the page `<head>` (capped 256KB) and never storing article text. Newsletter items are hard-excluded from image fetching and from the cache entirely (privacy rule).

## 3. Update cadence + pipeline (Grade A for the workflow file itself is B/source; A only for what's asserted as already shipped in the ship-decisions doc)

- Cron: `.github/workflows/curate.yml`, `cron: "17 * * * *"` (hourly, off the hour on purpose to avoid the busiest minute-0 slot), plus `workflow_dispatch` and a push trigger on changes to `topics.yaml`/`sources.yaml`/`curator/**`. `concurrency: group: pages, cancel-in-progress: false` prevents overlapping publishes. Note (repo's own doc comment): GitHub disables scheduled workflows after 60 days of repo inactivity.
- Three jobs, in order:
  1. `newsletter` job (secrets-scoped, `contents: read` only, its own `environment: newsletter`): runs `python -m curator.newsletter --root . --out ./newsletter_artifact.json` with Gmail OAuth secrets (`GMAIL_CLIENT_ID/SECRET/REFRESH_TOKEN`), uploads the JSON artifact. Never fails the build (`if: always()` downstream); a broken/expired token just produces a "dark" artifact.
  2. `build` job (`needs: newsletter`, `if: always()`, `contents: write` + `pages: write` + `id-token: write`): fetches HN/RSS/Reddit (`curator.pipeline`), consumes the newsletter artifact if present, runs `curator.pipeline --root . --out ./site --newsletter-artifact ./newsletter_artifact.json`, copies `static/` into `site/`, runs an inline Python "real content" verification (non-empty page, real story links, no unsafe schemes, per-tab counts, and a hard privacy assertion that no newsletter card ever carries an image or a link the sanitizer rejects, and no email-shaped query string reaches any href), then commits `image_cache.json` + `newsletter_state.json` back to `main` only if changed (`[skip ci]`), then uploads the Pages artifact.
  3. `deploy` job (`needs: build`): `actions/deploy-pages` -- deploys to **GitHub Pages** (not Cloudflare). Custom domain `news.joydong.org` is wired via GitHub Pages custom-domain settings + a DNS CNAME record (`news` -> `joydai2026-del.github.io`), NOT via a committed `CNAME` file in the repo (the design doc explicitly rules this out: "the Actions Pages workflow ... ignores it"). `render_site()` in `render.py` does have logic to copy a root `CNAME` file into `site/` if present, kept for fork compatibility, but the v2 design says this repo itself deploys with no CNAME file, Pages-settings-first.
- Pipeline stages (`curator/pipeline.py` docstring): `fetch -> age filter (48h default) -> dedupe -> keyword filter/category assignment -> rank -> render`. A publish guard refuses to overwrite a good page with an empty one if zero visible rows resulted (override with `--allow-empty`, used only by the CI offline smoke test).
- Sources: `sources.yaml` defines the shared RSS pool (19 feeds today) plus Hacker News / Reddit / newsletter tier config; `topics.yaml` defines the six category tabs, each with its own keyword list, optional aliases/excludes, optional native ("single-subject") curated feeds, and optional separate HN search queries. Today: 6 categories -- AI (33 kw/7 feeds), Crypto (40/8), Quantum computing (33/3), Energy and nuclear (41/8), Space technology (41/8), Biotechnology (41/5).
- `topics.yaml` purpose: the entire user-facing configuration surface. It is what the page's own "Add a topic or keyword" footer link deep-links to (GitHub's web file editor), so anyone with push/PR rights can add a keyword or a curated feed and it takes effect on the next hourly run -- there is no admin UI beyond GitHub itself.
- Newsletter lane: a 7th pseudo-category, id `newsletters` (reserved, config validation rejects a user category reusing that id/name). Kept structurally separate from the six regular categories:
  - Fetched in its own GitHub Actions job with its own secrets-scoped `environment`, no `contents: write`, all third-party actions pinned by commit SHA -- isolated so a compromised action in the main build job can never see Gmail credentials.
  - State: `newsletter_state.json` holds ONLY a timestamp watermark + salted content hashes (no message ids, no subjects, no sender addresses) -- confirmed by reading the actual file (58 hashes + a salt + a watermark, nothing else).
  - Cursor only advances after the page has been built and published successfully (`pipeline.py main()`), so a failed run re-reads the same overlap window rather than skipping mail.
  - Rendering: newsletter items get `is_newsletter=True`, `is_aggregator=True`, never get an image, never enter the image cache, and their URLs are passed through a link sanitizer (`curator/newsletter/sanitize.py`) that strips tracking params or, if it cannot recover a clean publisher URL, renders the headline unlinked rather than leaking a subscriber identifier. Lane has its own 50-item cap (`newsletter.max_items` in `sources.yaml`) and its own 48h retention window, independent of the six category caps.
  - Live adapters per the ship-decisions doc: tldr, theneuron, milkroad (+ therundown when it sends mail; bensbites parked/no adapter traffic in the surveyed week). `sources.yaml` lists `adapters: [tldr, therundown, bensbites, theneuron, milkroad]`.

## 4. Storage today (Grade B, measured directly)

- Whole repo on disk (working tree, excludes `.git`): 39M total, but this includes the `.venv` (Python virtualenv) and `.pytest_cache` -- the actual tracked data files are tiny:
  - `image_cache.json`: 44K on disk, 137 entries (URL -> {image, outcome, checked_at, seen_at}).
  - `newsletter_state.json`: 8.0K, 58 content hashes + one watermark + one salt.
  - `topics.yaml`: 20K, `sources.yaml`: 16K (both hand-edited config, not data).
  - `site/`: 16K (stale local sample; the real output is not committed to main, only ever exists as a CI artifact + the live gh-pages deploy).
- Nothing is ever pruned from git history -- both `image_cache.json` and `newsletter_state.json` are committed every hour they change ("chore: refresh image cache / newsletter cursor [skip ci]"), so their history grows the .git pack over time, but the live *content* of each file is actively pruned:
  - `ImageCache.prune()` drops any entry whose `seen_at` (last time that URL appeared as a live item) is older than `retain_days` (default 45 days, configurable, `retain_days: 0` is honored literally as "keep nothing").
  - `newsletter_state.json` only ever holds a fixed watermark + a rolling set of hashes for the current overlap window (the design doc specifies bounded, salted hashes for overlap dedup only, not a growing log).
  - Articles/items themselves are never stored at all outside of one in-memory pipeline run -- there is no historical archive of past headlines beyond what git history of `site/index.html` incidentally captured before the .gitignore change (site/ is now gitignored, so past renders are not even in git going forward).
- Growth rate (from git history of `image_cache.json`, all within the single day 2026-08-28, this repo's entire history so far): 28,463 bytes -> 41,445 bytes across 8 commits over roughly 11 hours, i.e. ~13KB growth in the first day, mostly the v1->v2 field migration plus 137 image entries accumulating. Too short a history (repo created 2026-08-28, "today" is 2026-08-29) to extrapolate a steady-state growth rate with confidence; growth should plateau once entries older than 45 days start pruning at the same rate new ones are added, but that steady state has not been observed yet in this repo (Grade C for any long-run projection).

## 5. Extensibility hooks (Grade B, source-verified)

- Categories/interests: `topics.yaml` is a fully data-driven config -- adding a category is adding a YAML block (name, keywords, optional aliases/excludes/sources/hn_queries); the config loader validates it strictly (rejects empty categories, duplicate ids/names, the reserved `newsletters` id). This is the only "personalization" surface that exists today, and it is repo-wide (one config, one audience), not per-viewer.
- No personalization, no saved searches, no user accounts, no server-side per-user state anywhere. The only client-side "memory" is `localStorage.setItem('nc-tab', ...)` remembering the last-selected category tab in one browser -- nothing else persists per visitor.
- No language/i18n support: confirmed by grep across `.py`/`.yaml`/`.md` -- no `language`/`i18n`/`locale`/`zh-`/Chinese-character hits anywhere except one keyword phrase "large language model" and a hardcoded `Accept-Language: en` header used only for image-meta HTTP fetches (not user-facing). No Chinese-content support, no multi-language UI strings, page is `<html lang="en">` and has `<meta name="robots" content="noindex">`.
- The "add a topic" flow (a footer link that opens GitHub's web file editor on `topics.yaml`) is explicitly the whole of the "how do I query/customize" story per the v2 design doc; the doc lists a "save/ask + wiki loop" (save-for-later, ask-and-research into JJ's private Obsidian vault) as explicitly OUT of v1 scope, described as a "Later" item requiring a private write path that does not exist yet.

## 6. Constraints -- locked decisions a redesign must not break

From `docs/plans/2026-08-25-news-curator-v2-design.md` ("Locked decisions, JJ, 2026-08-25") and `/Users/joyd/Documents/jj-knowledge-vault/agents/shared/decisions/2026-08-28-news-curator-v2-ship-decisions.md`:

- **Layout is locked to Discover Cards** (direction A of the 2026-08-25 inspiration board): responsive card grid, 3:2 image crop, headline + 2-line description, click-to-unfold in place, single-column swipe feed at phone width, Apple-minimal theme in light + dark. A redesign should treat this as the current baseline to evolve, not a green field.
- **The six category tabs stay**; a category is defined as a `topics.yaml` entry (keywords + curated sources) -- any redesign that changes categories must go through that file, not a new mechanism.
- **Cadence is hourly, unchanged.**
- **Domain is `news.joydong.org`, wired via GitHub Pages custom-domain settings + DNS, with NO CNAME file in the repo** (the Actions Pages workflow ignores a committed CNAME; the earlier CNAME-file approach was explicitly rejected in review).
- **Newsletter source account and its address must never be recorded in this public repo.** Nothing about the account, including the address, is committed anywhere.
- **Privacy gating (hard rule, must not regress):** newsletter items get no `og:image` fetch, no entry in the shared image cache ever, and links pass a sanitizer that strips tracking redirects/subscriber identifiers; if a clean publisher URL cannot be recovered, the item renders WITHOUT a link rather than risk leaking an identifier. Newsletter HTML is never rendered -- only escaped extracted text and validated URLs. Category matching for newsletter items uses the extracted story title only (never subjects or blurbs). A build-time assertion in `curate.yml` actively enforces this (fails the build if a newsletter card carries an image or a rejected link, or if any email-shaped query string reaches a rendered href) -- any redesign of the card markup must keep whatever markers (`data-newsletter`, `data-image`) that check keys off, or update the check in lockstep.
- **Newsletter lane semantics that must stay separate from the six categories:** its own tab (id `newsletters`, reserved and validated against collision), its own 50-item cap independent of category caps, same 48h retention window as everything else, present as a tab only when the lane is "lit" (non-dark) that hour -- no empty tab when dark. The lane must fail soft: a broken/expired OAuth token or adapter produces a "dark" artifact and a visible health note, never a failed pipeline run.
- **Allowlist-only newsletter parsing, not a generic parser:** live per-sender adapters only (tldr, theneuron, milkroad, + therundown when it sends); bensbites is parked (no adapter traffic observed); The Information and Brew Markets were explicitly and deliberately skipped ("if they're too complicated, we can just skip them") -- do not silently expand this list without a new decision.
- **OAuth app is published to production with permanent tokens** (not testing-mode, which expires after 7 days); this required filling in the app's home page (`https://news.joydong.org`), authorized domain (`joydong.org`), and a public privacy policy at `https://news.joydong.org/privacy.html` (shipped as `static/privacy.html`, PR #2) -- a redesign must keep that privacy page live at that exact path, since Google's OAuth consent screen links to it.
- **Lane fairness:** the newsletter cap uses round-robin per-sender allocation (`lane.fair_cap`), not a plain newest-first cut -- chosen specifically because newest-first starved smaller senders (The Rundown) in favor of the highest-volume one (TLDR).
- **DKIM/authentication trust is pinned** to the receiving server's own `Authentication-Results` header (`authserv_id` = `mx.google.com` by default); missing or foreign headers fail closed (message skipped). Not a redesign concern directly, but part of the newsletter lane's trust boundary that any UI change exposing "verified sender" status must not misrepresent.
- **Accuracy stance, must not be overstated by new copy:** the page promises only "the source handed us this title/description/link at build time," aggregator-authored headlines are labeled "via <source>," and nothing on the page is machine-generated or rewritten. Any new UI copy (badges, labels, etc.) must not imply stronger guarantees (e.g., "verified," "live," "fact-checked").
- **Follow-ups explicitly deferred, not yet done (do not assume these exist):** hash-pinned Python requirements in the secrets job; the page-wide email-leak check only inspects the query string of hrefs (accepted, documented scoping, not a bug to silently "fix" without revisiting the acceptance).
